## What I verified by reading and by experiment
- Reservation: one CAS on days/<ET date>; conflict, mini slot, cap and mini-slot-binding are all decided inside the same mutateLedger call. Cross-type and buffer overlap covered. Own-booking entries are excluded (reschedule).
- Buffer deviation (gap = max of the two buffers): CORRECT. Story 002 #3's example only works as "gap >= buffer" (a session ending exactly at 10:00 - B is offered), and api.md mini spacing (duration + buffer) only fits that rule. The ADR 0002 / architecture s9 sentence "busy intervals overlap" contradicts both and is stale. Max (not sum) is the right choice for mixed types (minis 10, others 30).
- Experiment (scratchpad, memory driver, 0-4 ms retry sleep): 16 parallel creates on 16 DISTINCT mini slots of one day gave 13 x 201 and 3 x 503 BUSY. 10 distinct: all 201. Production latency and 20-80 ms sleeps make it worse. BUSY is fail-safe and the UI handles it (src/booking/submit.ts).
- Reschedule is two-phase (reserve new, CAS booking, release old) even for the same date; ADR says one CAS for same date. Failure direction is safe (double hold, never zero).
- Transitions match architecture s8 and every PATCH/reschedule/delete carries expectedVersion, enforced inside updateBooking. Email outcome writes go through updateBooking without expectedVersion (merge only), fine.
- Idempotency: claim/replay/mismatch/in_progress/resume, claim kept once committed, released on any pre-commit error.
- DST/time: only shared/datetime imports luxon (lint-enforced); no Date parsing of business times elsewhere.
- Error codes match docs/api.md.

## Should fix
S1 ledger.ts prune skips verified entries, so a failed release leaks a hold that nothing heals (reschedule old slot; cancel/decline/complete). The documented retry (repeat cancel) is only reachable with a stale expectedVersion.
S2 CAS budget (5 tries, 20-80 ms flat) too small for a mini-day launch; 503s for the 6th-10th simultaneous family.
S3 reschedule undo path does not restore a same-start entry whose duration was changed.
S4 sendBookingEmails 10 s timeout runs inside the create request; no function timeout configured. A hung provider can push past the platform limit after the booking commits.
S5 createBooking uses loadWorldForType (today..horizon, up to 365 daily ledger reads) where loadWorld(date +-14) is enough.
S6 Tests missing: orphan pruning (ADR 0002 lists it as required), release failure, cross-date reschedule, BUSY path, reschedule racing a create.
Docs: ADR 0002 / architecture s9 / booking-domain-rules text still say busy-busy overlap; tests/helpers/builders.ts findOverlaps and tests/integration/qa/rules.test.ts "buffers" use busy-busy, which the real rule allows (the QA test passes only because its first slot is the 15:30 one with no neighbour at the boundary).
