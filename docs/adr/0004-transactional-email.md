# 0004. Transactional email and calendar file
Date: 2026-11-25 · Status: accepted

## Context
- v1 emails (stories 008, 013, 014, 020 and docs/design/emails.md): booking received (instant types), request received (Events), Daniella's new-booking notice, request approved, request declined, confirmed (deposit received or confirmed without payment), cancelled, rescheduled. The "hold expired" email is v1.1 (no auto-expiry in v1).
- Confirmation, approved, confirmed and rescheduled emails carry an `.ics`. Request-received and declined emails don't.
- An email failure must never roll back a booking. The booking is flagged "Email not sent" and can be resent (story 008 #5–6).
- Locally and in tests, no provider account. No PII in logs.
- Volume: tens of emails a month.

## Options considered
1. **Resend via its REST API with `fetch`.** Free plan: $0, 3,000 emails/month, 100/day, 3 domains, 30-day data retention; Pro $20/month for 50,000 (https://resend.com/pricing, checked 2026-11-25). API: `POST https://api.resend.com/emails` with `Authorization: Bearer <key>`. The body takes `from`, `to`, `subject`, `html`, `text`, `reply_to` and `attachments[]` (`filename`, `content` as Base64, optional `content_type`; max 40 MB per email after Base64). It supports an `Idempotency-Key` header (https://resend.com/docs/api-reference/emails/send-email, checked 2026-11-25). Pros: generous free tier, attachments, idempotency, simple DNS setup. Cons: one more vendor account.
2. **Postmark, SendGrid, Brevo, Amazon SES.** All workable, but SES needs AWS setup and the others give no real benefit at our volume. Not price-checked for this ADR.
3. **Netlify Email Integration.** It still needs an external provider underneath, so it adds a layer without removing the account.

## Decision
**Resend, called with `fetch` (no SDK), behind an `EmailSender` adapter. The `.ics` is generated by our own small module.**

```ts
// netlify/lib/email/sender.ts
export interface OutgoingEmail {
  kind: EmailKind;               // "booking_received" | "request_received" | "admin_new_booking" | "approved"
                                 // | "declined" | "confirmed" | "cancelled" | "rescheduled"
  bookingId: string;
  to: string; replyTo?: string;
  subject: string; text: string; html: string;
  attachments?: { filename: string; contentType: string; contentBase64: string }[];
  idempotencyKey: string;        // `${bookingId}:${kind}:${icsSequence}:${attempt}`
}
export interface EmailSender { send(msg: OutgoingEmail): Promise<{ providerId: string }> }
```
| `EMAIL_DRIVER` | Use | Behavior |
|---|---|---|
| `memory` | tests (default when `APP_ENV=test`) | Keeps sent messages in an array that tests can read. `failNext(n)` simulates outages. |
| `file` | local dev, e2e (default when `APP_ENV=local`) | Writes `<EMAIL_OUTBOX_DIR>/<ISO time>-<bookingId>-<kind>/` with `message.json` (headers), `body.txt`, `body.html` and the `.ics` (default dir `.data/outbox`, gitignored). Logs only `{kind, bookingId, path}`. |
| `resend` | previews and production | `fetch` POST with a 10-second `AbortSignal.timeout`. A non-2xx response or a timeout throws. |

Rules:
- **Sender** comes from config `email.fromName` and `email.fromAddress`; reply-to is `email.replyTo`. Daniella's notices go to `email.adminNotificationEmail`, with a link to the admin detail and no intake answers (story 008 #2).
- **Previews never email real clients:** when `EMAIL_REDIRECT_TO` is set, every message's `to` is replaced with that address and the subject is prefixed with `[preview → original recipient hidden]`. Guard: `APP_ENV` other than `production` with `EMAIL_DRIVER=resend` requires `EMAIL_REDIRECT_TO`.
- **Header injection:** recipient addresses are validated by the Zod email schema. Subjects are built from templates, and any client text in them has CR/LF stripped and is cut to 80 characters.
- **Body safety:** templates are TypeScript functions that return `{ subject, text, html }`. Every interpolated value goes through `escapeHtml` in HTML, and client-entered text is never turned into links (story 008 #8). Each email has a plain-text part.
- **Send after commit:** handlers send after the booking is stored, `await` the send (with the timeout), then record `emails[kind] = { status: "sent" | "failed", at, attempts, providerId? }` on the booking. The API response reports `emailSent: boolean`. Resend (`POST /api/admin/bookings/:id/resend-email`) re-sends the latest failed or chosen kind with a new attempt number. A repeated create request returns the stored response and never sends again.
- **Logs:** `{ kind, bookingId, driver, ok, providerStatus }` only.

### `.ics` (`netlify/lib/email/ics.ts`, about 80 lines)
RFC 5545 with CRLF line endings, lines folded at 75 octets, and `\`, `;`, `,` and newlines escaped. `METHOD:PUBLISH`, one `VEVENT`: `UID:<reference>@daniellabeltram.photography` (stable, so updates replace), `SEQUENCE:<booking.icsSequence>` (incremented on confirm and reschedule), `DTSTAMP`, `DTSTART`/`DTEND` in **UTC form** (`20261205T223000Z`, so it is DST-safe with no `VTIMEZONE` block), `SUMMARY`, `LOCATION`, `DESCRIPTION` per docs/design/emails.md §4, `STATUS:TENTATIVE` while pending deposit and `CONFIRMED` once confirmed, `ORGANIZER` set to the studio address, and a `VALARM` with `TRIGGER:-PT24H`. No client phone, email or intake answers. Filename: `daniella-beltram-photography-<YYYY-MM-DD>.ics`.

## Consequences
- Daniella creates a Resend account and verifies `daniellabeltram.photography` (or a subdomain such as `mail.daniellabeltram.photography`) by adding the SPF and DKIM DNS records Resend shows, plus a DMARC record (`v=DMARC1; p=none; rua=...` to start). devops writes the steps in `docs/operations.md`.
- `RESEND_API_KEY` is a secret env var (production and preview contexts; a separate key for previews is better).
- Resend keeps message data for 30 days on the free plan, so mention the email provider in the privacy notice (story 018).
- Revisit if volume goes past 100/day (minis launch day) → Resend Pro, or if deliverability is poor.
